# Phase 2 notes — FastAPI telemetry

Phase 2 answers two questions: **how does sensor data get in**, and **how does it
get back out live**. It is the whole storage and delivery story for the telemetry
service.

Scope: `backend/fastapi/` plus the one push Django makes into it. No frontend, no
ML inference (that is Phase 5).

The system is a **screening aid, not a medical diagnosis**. Nothing here produces
or stores a clinical finding.

---

## 2. Data model

One PostgreSQL schema, **`telemetry`**. No foreign key points at Django: the two
services share identifiers, not a database.

| Table | Key columns | Why it looks like this |
| --- | --- | --- |
| `known_sessions` | `session_id` UUID PK, `patient_id`, `device_id`, `doctor_ids`, `status` | the session registry (see §7) |
| `device_connections` | `device_id` UUID PK, `owner_id`, `last_seen`, `firmware_version`, `ip_address` | one row per device; the heartbeat reads `last_seen` |
| `sensor_readings` | `id` UUID PK, `session_id`, `device_id`, `sensor_type`, `value`, `unit`, `recorded_at` | **UNIQUE** `(session_id, sensor_type, recorded_at)` |
| `ecg_chunks` | `id` UUID PK, `session_id`, `device_id`, `start_time`, `sample_rate_hz`, `samples`, `sample_count`, `chunk_index` | **UNIQUE** `(session_id, chunk_index)` |
| `revoked_devices` | `device_id` UUID PK, `reason`, `revoked_at` | the deny list (see §8) |

Decisions worth defending in a review:

* **UUID primary keys generated by the application**, not by the database.
  Django generated the session and device UUIDs; the telemetry side must accept
  an identifier it did not create. `default=uuid.uuid4` also means the migration
  has no volatile server default, which is what lets the same migration run on
  SQLite in the test suite.
* **One row per ECG chunk, not per sample.** A 250 Hz, three-lead, one-hour
  session is 2.7 million samples; as chunks of 250 it is ~10 800 rows. `samples`
  is `JSONB` on PostgreSQL and `JSON` on SQLite, so the tests exercise the same
  code path.
* **`device_id` on every reading comes from the verified token**, never from the
  request body. A device cannot attribute data to another device even if it
  tries.
* **Idempotency is a database constraint.** The unique indexes are the
  guarantee; the pre-check exists only to return a friendly `duplicate: true`.
  A concurrent retry that loses the race catches `IntegrityError`, re-reads the
  winner's row and still answers `200`.
* **`TELEMETRY_SCHEMA=""` disables the schema.** SQLite has no schemas, so the
  suite turns it off; `config.py` refuses to start if SQLite and a schema are
  asked for together rather than silently creating tables it then cannot find.

## 3. Auth: verification is local, and the two audiences are separate

FastAPI holds the same `JWT_SIGNING_KEY` as Django and verifies tokens itself. No
endpoint calls Django to find out who is asking, so a Django outage does not stop
devices uploading.

| Property | How |
| --- | --- |
| Key | `JWT_SIGNING_KEY` from the environment, **no default** — the process fails at startup when it is missing |
| Algorithm | pinned to `["HS256"]`; `alg: none` and `alg: RS256` are rejected before the signature is checked |
| Expiry | verified by PyJWT; a token without `exp` is rejected |
| Device token | `type == "device"`, claims `device_id` (UUID) and `owner_id` (int) |
| User token | `token_type == "access"`, claims `user_id` (int) and `role` ∈ {patient, doctor, admin} |
| Wrong audience | a user token on a device endpoint → `401 Device token required.`; a device token on a user endpoint → `401 User access token required.` |
| Revocation | every device request does one primary-key lookup on `revoked_devices` |

`require_device`, `require_user` and `require_admin` in `core/security.py` are the
only ways into the app, so an endpoint cannot forget the check without failing to
have a principal at all.

**Why the WebSocket uses a query-string token.** A browser cannot set headers on
a WebSocket handshake, and the React dashboard is the main viewer. The
alternatives were a first-message handshake (more client code, an open
unauthenticated socket) or a cookie (there is none — JWTs are not stored in
cookies). The token is verified *before* the socket is accepted; on failure the
socket is accepted, sent one JSON error frame, and closed with `4401`/`4403`/
`4404`. The cost is that the token appears in access logs, which is written down
in the contract and mitigated by 60-minute access tokens. A one-time socket
ticket is the Phase 7 fix.

## 4. Endpoints

| Endpoint | Token | Success | Failure modes |
| --- | --- | --- | --- |
| `GET /` | none | `200` service name + disclaimer | — |
| `GET /health` | none | `200` | — |
| `POST /sensor/connect` | device | `200` heartbeat | 401 token, 403 revoked |
| `GET /sensor/status` | user | `200` device list + `online` | 401 token |
| `POST /sensor/data` | device | `200` `{stored, duplicate}` | 401, 403 (wrong device/revoked), 404 unknown session, 409 not active, 413 too large, 422 validation |
| `POST /sensor/ecg` | device | `200` `{stored, duplicate}` | as above |
| `GET /sessions/<id>/readings` | user | `200` newest first | 401, 403 not allowed, 404 unknown session, 422 bad `sensor_type` |
| `GET /sessions/<id>/ecg/<index>` | user | `200` samples | 401, 403, 404 no such chunk |
| `POST /internal/sessions` | user, admin | `200` upsert | 401, 403 not admin, 422 |
| `POST /internal/devices/<id>/revoke` | user, admin | `200` idempotent | 401, 403, 422 bad UUID |
| `WS /ws/sensor` | query string | snapshot + live frames | close 4401/4403/4404 |

Validation lives in `schemas.py`, never in an endpoint, so a bad frame cannot
reach the database and cannot become a 500: temperature 25–45 °C, SpO₂ 50–100 %,
pulse 20–250 bpm, motion 0–100 a.u., each with its own allowed unit spellings
(`°C`, `%`, `beats/min`, …) normalised to one canonical string. Timestamps may
not be more than `MAX_FUTURE_SECONDS` (300) ahead, nor before 2000-01-01.
`chunk_index` 0–1 000 000, `sample_rate_hz` 100–2 000, 1–5 000 samples per chunk,
each sample within ±20 mV, and the whole body at most 1 MiB
(`413` from middleware, before parsing).

Everything that fails answers with the same object, and an unknown route or an
unhandled exception is still JSON:

```json
{"detail": "…", "code": "machine_readable", "errors": [{"field": "value", "message": "…"}]}
```

## 5. Live delivery

`hub.py` keeps one `asyncio.Queue` per viewer, keyed by session. After a
successful commit, `POST /sensor/data` publishes a `reading` frame and
`POST /sensor/ecg` publishes an `ecg_chunk` frame **carrying metadata only** —
pushing 5 000 samples down every viewer socket is what the REST endpoint is for.
A duplicate is not re-broadcast, so a viewer sees each reading once.

The socket pumps both directions at once (`asyncio.wait` on
`receive_text()` and the queue), so a viewer that never sends anything still gets
live frames, and a disconnected client is noticed instead of being kept alive by
an idle queue. A queue that fills up (a wedged client) drops frames and logs,
rather than growing until the server runs out of memory.

## 6. The push from Django

`backend/django/monitoring/telemetry.py` POSTs each new session (and each
`stop`) to `/internal/sessions`, authenticated with a short-lived admin token
Django mints for itself (`role: "admin"`, five-minute lifetime).
`SessionViewSet.perform_create` and `.stop` call it.

* **Best effort**: if FastAPI is down, the session is still created; Django logs
  a warning and moves on. A telemetry outage must not block clinical workflow.
* **Synchronous, stdlib only**: one `urllib` POST with a 2 s timeout. Fine at
  demo scale; a queue with retries is the correct production shape.
* **Replayable**: the endpoint is an upsert, so re-sending repairs a stale cache.
* Tests set `TELEMETRY_SYNC_ENABLED=False`, so the suite never waits on another
  service.

## 7. Viewer access without calling Django

The registry carries `patient_id` and `doctor_ids`, which is everything the
access rule needs:

| Caller | May see a session when |
| --- | --- |
| admin | always |
| doctor | their `user_id` is in `doctor_ids` |
| patient | their `user_id` is the session's `patient_id` |
| device token | the token's `device_id` is the session's device (so the simulator can watch its own uploads) |

That is what `GET /sessions/<id>/readings`, `GET /sessions/<id>/ecg/<index>` and
the WebSocket check. It is enforced from the registry snapshot, which is the
tradeoff in §9.

## 8. Revocation

Device tokens are stateless: neither service can invalidate one already issued,
and Django's "disable device" only blocks *new* tokens and *new* sessions.
FastAPI therefore owns a small deny list and checks it with one primary-key
lookup on every device request. `POST /internal/devices/<id>/revoke` (admin
token) adds a row; `GET /sensor/status` reports `revoked: true` so the dashboard
can show it. It stays small because it is one row per device, and there is no
`DELETE` yet — un-revoking is Phase 7 work, together with wiring Django's disable
button to this endpoint.

## 10. Deliberate limits

* **Stateless dev tokens.** Only the deny list cuts a device off early; there is
  no per-token revocation, no `DELETE` to un-revoke.
* **The registry is a cache.** If a push is lost, a legitimate device gets
  `404 unknown_session` until the next successful push. There is no automatic
  reconciliation yet — replaying `/internal/sessions` repairs it, and a periodic
  replay job is the Phase 7 fix. A completed session stays in the registry with
  `status: completed`, so late data is `409`, not `404`.
* **Viewer access uses the snapshot.** A doctor assigned *after* a session
  started sees it only after the next push; reassignment mid-session needs
  another push.
* **In-process fan-out.** Two FastAPI workers each reach only their own viewers.
  Redis pub/sub is the Phase 7 fix.
* **The WebSocket token is in the URL**, so it lands in access logs.
* **No rate limiting and no retention.** A runaway device can fill the tables;
  `sensor_readings` and `ecg_chunks` grow forever.
* **ECG storage is raw.** No filtering, no waveform reconstruction, no inference
  — that is Phase 5.
* **`limit` is the only pagination** on the readings endpoint (default 100, max
  500).
* **SQLite is the local default.** Good enough for development and the test
  suite, but the schema, `JSONB` and concurrent writers are PostgreSQL features;
  production must run Postgres.

## 11. Decisions made while building this (recorded, as requested)

1. **The contract was written first** (`docs/api-contract.md`), then the code was
   made to match it; the two are checked against each other in the final pass.
2. **Unknown sessions are a push, not a call back to Django.** It keeps Django
   off the ingest path; the cost is a cache that can go stale, which §10 states.
3. **Viewer access is enforced from the registry**, so it needs no Django call
   and no new endpoint. The limitation is the snapshot, in §10.
4. **SELECT-then-INSERT instead of `ON CONFLICT DO UPDATE`** for the two upserts
   (device connection, session registry). The dialect-specific clause does not
   exist on SQLite, and losing the test suite to save one round trip on an
   endpoint that fires a few times a day is a bad trade.
5. **Both the smoke script and a pytest suite were written**; the script is what
   proves the journey end to end, the suite is what keeps it true.
6. **Django's answers were verified live**: with the real dev server, a device
   token minted by Django stored a temperature reading (`200`, `stored: true`), a
   repeated reading returned `duplicate: true` with the same `reading_id`, the
   same ECG chunk twice returned one `chunk_id`, a bad token answered `401`, a
   99 °C reading answered `422`, an unknown session answered `404`, a device
   token on a user endpoint answered `401`, and a WebSocket client received a
   `reading` frame live. The transcript is in `docs/phase-2-smoke-test.md`.
7. **Timestamps in tests are relative to the wall clock**, because the
   "not absurdly in the future" rule turned a fixed literal into a 422 the moment
   the machine clock passed it — which is exactly the kind of test that fails
   six months later for no reason.
