# Phase 1 notes — identity, access and sessions

Phase 1 answers two questions: **who exists**, and **what may they do**. It is
the whole authorisation story for the Django service; nothing here is
speculative scaffolding for later phases.

Scope: `backend/django/` only. No frontend, no FastAPI, no Postgres.

This system is a **screening aid, not a medical diagnosis**. Nothing it stores
or shows is a clinical finding; every user-facing label has to say so.

## 2. Data model

### User, and why the profiles are separate tables

`accounts.User` extends `AbstractUser` (so username, password hashing,
permissions and admin integration keep working) and adds one field:

```python
class Role(models.TextChoices):
    PATIENT = "patient", "Patient"
    DOCTOR  = "doctor",  "Doctor"
    ADMIN   = "admin",   "Admin"
```

`PatientProfile` (date_of_birth, notes) and `DoctorProfile` (speciality) are
`OneToOneField`s to `User`. The alternative — putting every field on `User` —
produces a wide table that is mostly NULL for any given row, and makes a
patient-only migration touch the authentication table.

Both profiles have a `clean()` that checks the linked user's role. That method
runs through `full_clean()`, i.e. from the admin and forms; it is **not** called
by `objects.create()` or `save()`. Role pairing is therefore guaranteed for
data created through the admin and through `seed_demo`, not for arbitrary ORM
writes. This is a deliberate, documented limit rather than an oversight.

### Doctor-to-patient assignment

```python
class DoctorAssignment(models.Model):
    doctor     = FK(DoctorProfile)
    patient    = FK(PatientProfile)
    created_at = DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [UniqueConstraint(fields=["doctor", "patient"],
                                         name="unique_doctor_patient")]
```

`DoctorProfile.patients` is a `ManyToManyField(PatientProfile, through="DoctorAssignment")`.
The explicit through model is what makes `created_at` possible and what carries
the uniqueness rule; a plain M2M has nowhere to put either. It also removes
`.add()` / `.set()`, so a duplicate assignment cannot be created through the
M2M API at all — reads use `doctor.patients.all()`, writes go through
`DoctorAssignment.objects.create(...)`.

`UniqueConstraint` is used rather than `unique_together` because it accepts a
`condition=`, which is exactly what the session rule below needs.

### Device and Session use UUID primary keys

```python
id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
```

FastAPI will later store `device_id` and `session_id` as **plain UUID values in
its own tables, with no foreign key back to Django**. An auto-increment integer
would only be unique inside the Django database; a UUID is generated by Django
and can be referenced by another service with no lookup and no shared sequence.

### Only one active session per device

```python
constraints = [
    UniqueConstraint(fields=["device"],
                     condition=Q(status="active"),
                     name="unique_active_session_per_device"),
]
```

This is a **partial unique index**: it applies to active rows only, so a
completed session does not block the device from being used again. Because it
lives in the database, it also closes the race in which two concurrent requests
both pass an application-level check. The serializer still checks first, purely
to return a readable 400 instead of a 500.

## 3. Authentication (SimpleJWT)

| Endpoint | Purpose |
| --- | --- |
| `POST /api/auth/login/` | username + password → `access` + `refresh` |
| `POST /api/auth/refresh/` | `refresh` → new `access` |
| `GET /api/auth/me/` | current user: `id`, `username`, `role` |

The access token carries the claims FastAPI needs, added by
`RoleTokenObtainPairSerializer.get_token()`:

```json
{"token_type": "access", "exp": 1750000000, "iat": 1749996400,
 "jti": "...", "user_id": 7, "role": "doctor"}
```

`SIGNING_KEY` is read from `JWT_SIGNING_KEY` and is deliberately **separate from
`SECRET_KEY`**. `SECRET_KEY` protects Django sessions, password-reset links and
signed cookies; `JWT_SIGNING_KEY` is shared with another service. Rotating one
must not invalidate the other, and only the JWT key ever leaves this process.

Both are read from the environment by `config/env.py::require_env()` with **no
default and no fallback to each other**: a missing `DJANGO_SECRET_KEY` or
`JWT_SIGNING_KEY` stops the process at import time with `ImproperlyConfigured`
instead of signing real tokens with a value that is committed to the repository.
Development and test values live in `.env.example` and `pytest.ini`/`conftest.py`
only, never in `settings.py`.

Lifetimes: access 60 minutes, refresh 7 days.

## 4. Device tokens, and how FastAPI verifies them locally

`POST /api/devices/` registers a device and returns a signed token **once**:

```json
{"type": "device", "device_id": "3f1c...-...", "owner_id": 7,
 "iat": 1749996400, "exp": 1781532400}
```

* Signed with the same `JWT_SIGNING_KEY`, same HS256 algorithm.
* Lifetime 365 days — a device cannot perform an interactive login.
* **Never stored in the database.** It is a bearer credential; the API cannot
  read it back. Losing it means rotating it
  (`POST /api/devices/<id>/rotate-token/`, owner or admin), not looking it up.
* `type: "device"` is what keeps the two token audiences apart: a user access
  token presented to a device endpoint must be rejected, and vice versa.
* A device whose `status` is `disabled` is refused a token (**400**, field-level
  error on `device` when starting a session; **400** with `detail` when
  rotating). Rotation returns 400 rather than 403 because the caller *is*
  allowed to rotate their own device — it is the device's state that makes the
  request unprocessable. The status is already visible to the owner in
  `GET /api/devices/`, so nothing is leaked.

### What disabling and rotating do *not* do

Neither revokes a token that has already been issued. Device tokens are
stateless: Django stores nothing about them, so it cannot invalidate one that is
already in a device's flash memory. Rotation issues a *new* token and the old
one keeps verifying until its `exp`. Disabling blocks the Django API from
issuing *more* tokens and from starting sessions, but a previously issued token
still works against FastAPI until it expires — or until `JWT_SIGNING_KEY` is
rotated for every device at once. Per-device revocation is Phase 2 work (a
FastAPI-owned `revoked_devices` table); `devices/tokens.py` says the same thing
at the point of use.

### FastAPI side (Phase 2)

FastAPI holds the same `JWT_SIGNING_KEY` in its own `.env` and verifies the
signature itself — no call back to Django:

```python
import jwt
from fastapi import Header, HTTPException

ALGORITHM = "HS256"

def decode_device_token(authorization: str = Header(...)) -> dict:
    token = authorization.removeprefix("Bearer ").strip()
    try:
        claims = jwt.decode(token, settings.jwt_signing_key, algorithms=[ALGORITHM])
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Invalid device token")
    if claims.get("type") != "device":
        raise HTTPException(status_code=401, detail="Not a device token")
    return claims          # device_id, owner_id usable as-is
```

* `jwt.decode` verifies the signature and `exp`; `algorithms=["HS256"]` must be
  pinned, otherwise a token could claim `alg: none`.
* `device_id` and `owner_id` are read straight out of the token and stored as
  plain UUID / integer columns — that is why the Django models use UUID keys.
* Verification is local, so a Django outage does not stop devices from
  uploading data. The cost is that revocation is not instant: a token stays
  valid until it expires or until `JWT_SIGNING_KEY` is rotated. A per-device
  revocation list (checking `device_id` against a table FastAPI owns) is the
  Phase 2 answer if that becomes a requirement.

## 5. Permission model

**Today, endpoint access is enforced by three things:**

1. `IsDoctorOrAdmin` as a view-level gate on the device and session writes;
2. `get_permissions()` role gating in `SessionViewSet` — a patient asking for
   `create` or `stop` gets **403** before any object is looked up;
3. queryset filtering, so a row the caller may not see is simply not in the
   queryset and `get_object()` raises **404** — an unauthorised object does not
   leak even its existence, which a 403 would.

The remaining classes in `accounts/permissions.py` — `IsAdminRole`,
`IsDoctorRole`, `IsPatientRole`, `IsAssignedDoctor` and `IsOwnerOrAdmin` — are
**implemented and unit-tested but not wired to any endpoint**. They are kept
deliberately (and not deleted) for **Phase 6**, where object-level rules stop
being expressible as a queryset filter: reports, the doctor view and the admin
dashboard need to ask "may this caller touch this object?" for a specific object
that is already in hand. Each carries the docstring *"Reserved for Phase 6, not
yet used by any view."*

### Where each class is used

| Class | Used where today |
| --- | --- |
| `IsDoctorOrAdmin` | `DeviceViewSet.permission_classes`, and `SessionViewSet.create` / `SessionViewSet.stop` via `get_permissions()` |
| `IsAuthenticated` (DRF) | `MeView`, `PatientProfileViewSet`, `SessionViewSet` reads |
| `IsAdminRole` | nothing — reserved for Phase 6 (admin dashboard) |
| `IsDoctorRole` | nothing — reserved for Phase 6 (doctor view) |
| `IsPatientRole` | nothing — reserved for Phase 6 (patient report view) |
| `IsAssignedDoctor` | nothing — reserved for Phase 6 object-level checks on reports/sessions |
| `IsOwnerOrAdmin` | nothing — reserved for Phase 6 object-level checks on devices/records |

### Endpoints and who may call them

| Endpoint | Patient | Doctor | Admin |
| --- | --- | --- | --- |
| `GET /api/health/` | public | public | public |
| `POST /api/auth/login/` | public | public | public |
| `POST /api/auth/refresh/` | public | public | public |
| `GET /api/auth/me/` | self | self | self |
| `GET /api/patients/` | self only | assigned only | all |
| `GET /api/patients/<id>/` | self, else 404 | assigned, else 404 | all |
| `GET /api/devices/` | 403 | own only | all |
| `POST /api/devices/` | 403 | creates own | creates own |
| `POST /api/devices/<id>/rotate-token/` | 403 | own, else 404; 400 if disabled | any; 400 if disabled |
| `GET /api/sessions/` | own only | assigned patients | all |
| `GET /api/sessions/<id>/` | own, else 404 | assigned, else 404 | all |
| `POST /api/sessions/` | 403 | assigned patient + own + enabled device | any patient + any enabled device |
| `POST /api/sessions/<id>/stop/` | 403 | assigned, else 404 | any |

`GET /api/health/` is a plain Django view (not DRF), so it has no permission
class and answers `{"status": "ok", "service": "django"}` to anyone; it is a
liveness probe, carries no data and is the endpoint the frontend polls.

`GET /api/sessions/<id>/` is the read-only `retrieve` action of
`SessionViewSet`, so it goes through the same `get_queryset()` filter as the
list: a patient sees their own session, a doctor sees sessions of patients they
are assigned to, an admin sees all — and everybody else gets **404**.

"Assigned patient + own device" is validated in `SessionSerializer.validate()`
and answers **400** with a field-level message (`patient` / `device`), because
the request is a creation with invalid input rather than an attempt to read
someone else's object. A disabled device is refused in the same place, before
ownership and assignment are even considered, so it answers identically
whoever asks. These rules are tested.

Patients may read their own sessions but may not start or stop one: reading is
scoped by role in `get_permissions()`.

## 6. Demo data

```powershell
python manage.py seed_demo
```

Idempotent. It creates, with password `demo12345`:

| Username | Role | Notes |
| --- | --- | --- |
| `admin` | admin | `is_staff` + `is_superuser`, so `/admin/` is usable |
| `doctor1` | doctor | Cardiology — assigned `patient1`, `patient2` |
| `doctor2` | doctor | Neurology — assigned `patient3`, `patient4` |
| `patient1`…`patient4` | patient | two per doctor |

The seeded `admin` is a Django superuser. That is intentional — otherwise the
admin site the phase registers models into cannot be inspected — but it does
mean the demo password grants full admin access. Change it outside a demo.

`accounts.UserManager` keeps `role` in step with the staff/superuser flags:
`create_superuser()` and `create_user(is_staff=True)` now set
`role=Role.ADMIN` unless the caller passes an explicit `role=`. Before that,
`manage.py createsuperuser` produced a user whose role fell back to the column
default, "patient", so the new administrator could open `/admin/` but was
refused by every role-gated API endpoint.

Devices are **not** seeded: they are created through the API so that the device
token flow (issue-once, rotate) is exercised rather than pre-filled.

## 7. Tests

```powershell
cd backend/django
pip install -r requirements-dev.txt
pytest
```

`pytest.ini` sets `DJANGO_SETTINGS_MODULE=config.settings`, adds `tests.py` to
`python_files` (because `startapp` generates `tests.py`, which pytest does not
collect by default), disables the cache provider and pins `--basetemp` inside the
project. `conftest.py` provides the fixture graph: two doctors who each own a
device, one patient assigned to each, plus a disabled device, and it sets the two
test-only secrets before Django settings are imported (settings has no fallback).

Current state: **43 passed, 1 skipped**. The skip is
`accounts/test_users.py::test_django_refuses_to_start_without_the_secrets`, which
starts a subprocess with the secrets removed to prove the startup failure is
real. It is skipped because this Windows workspace denies the subprocess pipes
and temp directories it needs — an environment limit, not a code bug. The
in-process half of the same guarantee (`require_env` raising
`ImproperlyConfigured` for a missing or blank key) still runs.

Two stale cache directories (`pytest-cache-files-88wctrkw`, `.pytest_cache`) were
created before the cache provider was disabled. The sandbox does not let them be
deleted, so a run adds `--ignore=pytest-cache-files-88wctrkw`:

```powershell
pytest --ignore=pytest-cache-files-88wctrkw
```

Covered:

* doctor A cannot list or open doctor B's patients (list → only A's, detail → 404)
* a patient sees only themselves, and another patient's detail is 404
* a patient cannot register a device (403) or start a session (403)
* a doctor cannot start a session for an unassigned patient (400)
* a doctor cannot use another doctor's device (400)
* a disabled device cannot start a session (400) and cannot be handed a rotated
  token (400), while staying visible to its owner
* a session detail is readable by the patient and the assigned doctor and is 404
  for everybody else
* a device cannot have two active sessions — at the API (400) **and** at the
  database (IntegrityError) — and can be reused once the session is stopped
* the access token carries `user_id` and `role`
* the device token decodes with `type="device"` and the right `device_id`
* the device token is returned once and never appears in the device list
* `create_superuser()` and `create_user(is_staff=True)` produce an admin role,
  a plain `create_user()` produces a patient, and an explicit role wins
* `require_env` returns a trimmed value and raises `ImproperlyConfigured` for a
  missing or blank key
* every permission class — including the five no view uses yet — answers
  correctly for a patient, an assigned doctor, an unassigned doctor and an admin

## 8. Deliberate limits (Phase 2 candidates)

* No device revocation list — an issued device token stays valid until it
  expires or the signing key is rotated (see §4). Phase 2 adds the FastAPI-owned
  `revoked_devices` check; disabling a device in Django today does not yet write
  that row.
* `Session.status = "aborted"` exists in the model but no endpoint sets it.
* No `start_time` override, no session heartbeat/ingest — that is the FastAPI
  side, which will store samples against the UUID `session_id`.
* Role pairing for profiles is enforced in `clean()` (admin/forms) only.
* No pagination or filtering on the list endpoints; fine at demo scale.
* SQLite, no Postgres. FastAPI will use Postgres in its own `telemetry` schema.

## 9. Changes after review

Review of Phase 1 found four issues; all four are fixed and tested.

1. **JWT signing key was allowed to fall back to `SECRET_KEY`, and `SECRET_KEY`
   had a hard-coded default.** Both now come from `require_env()` with no
   default (see §3); a missing key raises `ImproperlyConfigured` at startup.
   Dev/test values live only in `.env.example` and `pytest.ini` + `conftest.py`.
   `test_require_env_*` cover the helper; the subprocess startup test is skipped
   for the Windows temp-directory reason described in §7.
2. **The unused permission classes were about to be deleted as dead code.** They
   are kept on purpose, each now carries *"Reserved for Phase 6, not yet used by
   any view."*, §5 states plainly that today's enforcement is
   `IsDoctorOrAdmin` + `get_permissions()` + queryset filtering (404), and a
   table lists which class is used where. All five have unit tests over the
   four-role matrix.
3. **Disabled devices could still start sessions and still be issued tokens.**
   `SessionSerializer.validate()` rejects them with a field-level error on
   `device`, and `rotate_token` returns 400 — 400 rather than 403 because the
   caller is allowed; the device's state is what blocks the request (§4). The
   `tokens.py` docstring now says honestly that rotating or disabling does *not*
   revoke an already-issued stateless token, and points at Phase 2.
   `test_disabled_device_cannot_start_a_session` and
   `test_disabled_device_cannot_get_a_rotated_token` cover both.
4. **Small omissions.** `GET /api/health/` and `GET /api/sessions/<id>/` are in
   the endpoint table of §5 with per-role permissions, and session detail has
   own/assigned-only tests (everyone else gets 404). `create_superuser()` now
   sets `role=ADMIN` via `accounts.UserManager` (§6) with tests. Every path in
   this document matches the folder on disk: the repository folders are
   lower-case, so all references use `backend/…` consistently.
